# `Q_web_admin` — does a browser UI ever come back?

**Answered for v1: no UI.** The admin interface is an SSH login to the box and `dokku` / `shepherd2`
commands issued by hand, with `README.md` → *Day-to-day operations* documenting every common scenario as
the exact command. That is the whole of v1, and it is what `D_retire_shepherd_java` and
`D_dokku_is_truth` decided. This note is the standing question, `Q_web_admin`; both of those
entries, `D_ruby`, `D_stats` and `D_admin_namespace` point here.

**The property any answer must have** is the one `D_dokku_is_truth` requires: it is a *client* of
Dokku's state, storing nothing authoritative of its own. A UI that keeps its own project records is the
descriptor through the back door, and that is not on the table. A hostname is already waiting for
whichever of these wins — `create-app` reserves the whole `admin*` prefix (`D_admin_namespace`) and the
wildcard certificate covers it.

## The four candidates, none decided

1. **A read-only status page** generated by cron from `dokku *:report --format json` and served as
   static files. No auth to get wrong, no framework, and it covers "is everything up" without covering
   "administer the box". Cheapest thing that answers the question people actually ask.
2. **wharf**, adopted as a pure client — day-N edits and logs in a browser. 262★, AGPL-3.0,
   single-maintainer, alive; scope is day-to-day (apps, env vars, domains, deploy, logs) and *not*
   provisioning (nothing for resource limits, `docker-options` or networks). It talks to Dokku over SSH
   with a key of its own and authenticates its own users with a single `ADMIN_PASSWORD`, so it is
   single-operator only — and nothing server-side lives in it, so there is nothing to lose if it dies
   (`D_dokku_is_truth` → *Consequences*). `research.md` → *Admin interface* has the survey it sits in.
3. **Re-programme shepherd-java-client as a Dokku client**, once `create-app`'s command set has
   solidified: stop storing `/etc/shepherd/java/projects/*.json`, read `*:report --format json` for the
   project list, and edit by emitting `dokku` / `shepherd2` commands. The existing Vaadin Web Admin then
   drives a shepherd2-dokku box unchanged on the surface. This is the first road-not-taken in
   `D_retire_shepherd_java` reopened, and **the only option that gives back per-owner project lists and
   Google SSO** without Dokku Pro — see `ideas/multi-user-ownership.md`. The flavour that keeps the JSON
   files as truth is *not* on the table.
4. **A TUI in Ruby on [Tuile](https://github.com/mvysny/tuile).** Same client shape as 3 with no
   browser, no auth of its own and no JVM: it runs in the operator's SSH session and shells out to
   `dokku` / `shepherd2`, so it is v1's cheat sheet made interactive. Prior art for the shape is the
   Ruby `dokku-cli` gem (Dokku lists no TUI at all). Cheapest of the four to build, the one that adds
   no new surface to the box, and the one `D_ruby` already leans toward by putting Ruby on the box.

Dokku Pro is not on this list: it is the official web UI, and `D_retire_shepherd_java` rejected it for
being paid and proprietary. Third-party UIs other than wharf are a graveyard — `ledokku` (the one Dokku
itself endorsed, in 2021) died 2023, as did `atlas` and `HarborJS`; that death rate is an argument
about the whole class, and it is why option 1 or 4 beats option 2 on anything but immediate effort.
